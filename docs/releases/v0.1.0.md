# whirl-ui v0.1.0

Whirl is a lightweight tray frontend for the [whirl](https://github.com/guruor/whirl) wallpaper daemon.
The daemon is headless: it owns the wallpaper, the rotation, the sources and every piece of state, and
this app is a client of it. It puts the daemon on the menu bar, where the rows show what the daemon
reports and send the daemon's own verbs, and **Settings…** opens a window over the daemon's effective
plan. The app writes no state file, sets no wallpaper itself, and never starts, stops or restarts the
daemon.

This release is **macOS only**: Apple silicon, macOS 13 or later. Windows and Linux are M4 in
[`docs/milestones.md`](../milestones.md); this release carries no build for either.

## Which build this is

The release carries one archive, built from the tagged commit by
[`.github/workflows/release.yml`](../../.github/workflows/release.yml):

    Whirl-0.1.0.zip          Whirl.app, the app bundle, at the archive's root
    Whirl-0.1.0.zip.sha256   the archive's sha256, published beside it

`Whirl.app` is `com.guruor.whirl-ui`: an agent app (`LSUIElement`), so it has no Dock icon and opens no
window of its own until you ask for one from its menu bar item.

The version is the tag. The tag is `v0.1.0`; `scripts/make-bundle.sh` strips the leading `v`, which is
why the bundle's `CFBundleShortVersionString` and the archive's own name are `0.1.0` without it. The
same script writes both files, and a hand run with no tag and no version argument writes a `-local`
build that says what it is instead of borrowing a version it did not come from.

The archive is build output, not source, and nothing about it is committed: the file attached to this
release is the one the workflow built from the tagged commit. The tag itself is cut on `main`; the
workflow's first job refuses to publish from a tag that is not on `main`, so a release is always the
commit a reader can find in `main`'s history.

## Install

There are two routes and one outcome. Both are written out, step by step, in a single place:
[`docs/installation.md`](../installation.md).

- **Route A, one command**: fetch `install.sh` from this tag, read it, then run it. It installs the
  daemon and the app, checking each archive against the sha256 published beside it before anything is
  unpacked.
- **Route B, by hand**: the same work typed out, from the Rust toolchain and the daemon's three
  binaries to a picture on the desktop and the tray app talking to the daemon.

This document does not repeat those steps. `docs/installation.md` is their home, and it is the place
to read before installing.

## The signature, and the first launch of a downloaded copy

The app is **ad-hoc signed** and **not notarized**. There is no Developer ID behind this release:
nothing on the machine verifies who built it, and `spctl -a -vv` refuses the bundle, which is expected
rather than a failure. An ad-hoc signature covers the app's own bytes, so it says the bundle was not
modified after signing and says nothing about who signed it.

macOS puts `com.apple.quarantine` on anything it can tell arrived from the network, a browser download
included. Launch a quarantined copy and Gatekeeper refuses it: the app does not open, and the dialog
offers to move it to the Bin or to cancel the launch. Apple's wording in that dialog moves between
releases; the refusal and the way through it do not. The way through is to launch it once and refuse
it, then allow it under **System Settings → Privacy & Security → Open Anyway**, or to clear the flag
before launching:

    xattr -dr com.apple.quarantine /Applications/Whirl.app

Quit the app first if it is running: removing the attribute from a copy that is still up is refused
with `Operation not permitted`. A copy you built or installed on this machine carries no quarantine
flag and needs none of this, and route A clears the flag on a downloaded copy itself, after its own
checksum check has passed.

## What the published checksum proves

The `.sha256` beside the archive is what it says: the archive's sha256, so it can be checked directly.

    shasum -a 256 -c Whirl-0.1.0.zip.sha256
    Whirl-0.1.0.zip: OK

It proves that the bytes you have are the bytes the release job built. A truncated or altered download
fails the check before anything is unpacked, and both install routes refuse it rather than installing
something they cannot vouch for. It proves nothing about who built them: the digest is published next
to the archive over the same connection, so whoever can replace one can replace the other. It is a
delivery check, not an identity, and it is not a signature.

## Known limits

- **Unregistering the login item leaves a record.** The app registers its own login item through
  `SMAppService`, and `--login-item unregister` removes it from the Login Items pane. The Background
  Task Management database keeps the app's row as `Disposition: [disabled, allowed, notified]`, because
  `SMAppService` has no delete and the row survives the bundle being moved. Nothing a person can see in
  the Login Items pane outlives an unregister; the database row does. It is stated in
  [`docs/milestones.md`](../milestones.md) M3 criterion 1 as well as here.
- **macOS only, in this release.** The tray item and the login item are macOS code, and the release
  ships only `Whirl.app`, for Apple silicon. There is no Windows or Linux artifact.
- **Nothing starts the daemon for you.** The app never starts, stops or restarts whirl, whirl v0.1.0
  ships no installer for its own login unit, and the app's login item is not registered for you. So
  after a reboot neither the daemon nor the app is running until you start the daemon and register the
  app's login item yourself.
