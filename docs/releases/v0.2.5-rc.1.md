# whirl-ui v0.2.5-rc.1

Whirl is a lightweight tray frontend for the [whirl](https://github.com/guruor/whirl) wallpaper daemon.
The daemon is headless: it owns the wallpaper, the rotation, the sources and every piece of state, and
this app is a client of it. It puts the daemon on the menu bar, where the rows show what the daemon
reports and send the daemon's own verbs, and **Settings…** opens a window over the daemon's effective
plan. The app writes no state file, sets no wallpaper itself, and starts no process of its own.

This release is **macOS only**: Apple silicon, macOS 13 or later.

This is a **candidate**, not the release. It is published as a GitHub prerelease, so it is not offered
as this repository's latest release, and `install.sh` run with no override still installs the released
pair (`Whirl 0.2.4` and `whirl v0.2.1`). What opts into it is the channel,
`WHIRL_CHANNEL=unstable`, which resolves it, or the two version overrides, which name it.

## Which build this is

The release carries one archive, built from the tagged commit by
[`.github/workflows/release.yml`](../../.github/workflows/release.yml):

    Whirl-0.2.5-rc.1.zip          Whirl.app, the app bundle, at the archive's root
    Whirl-0.2.5-rc.1.zip.sha256   the archive's sha256, published beside it

The version is the tag: `v0.2.5-rc.1`, with the leading `v` stripped by `scripts/make-bundle.sh`, and
the bundle's `CFBundleShortVersionString` is the same string.

## What changed since v0.2.4

The unstable build can be installed. Until now the word for it was in the installer and nothing read
it: `install.sh` documented `WHIRL_CHANNEL` as reserved, and a run that set it installed the pinned
pair anyway, so an instruction that used it would have been a lie. It is read now, and this candidate
is the other half: the channel resolves a prerelease of this repository, and there was none to resolve.

- **`WHIRL_CHANNEL=unstable` resolves a pair and installs it.** It reads each repository's release
  list, takes that repository's newest published prerelease, prints both tags before either archive is
  fetched, installs the pair, and writes both tags into the receipt, because the command no longer says
  which pair was installed. A draft release is not published and is passed over, and the tags are
  compared as versions rather than taken in the order the list carries them, so the answer is the
  newest prerelease and not the most recently opened one. `install.sh --help` names the two lists it
  reads, which are overridable, and `scripts/test-install.sh` pins the resolution against stand-ins.
- **A run that cannot resolve stops instead of installing something else.** Three ways: a repository
  whose release list holds no prerelease (the words name the repository, and nothing is installed in
  its place), a channel value this script does not know (refused by name), and a version override
  beside a channel, where the pair would no longer be the one the channel resolved. A release list it
  cannot read is a fourth: the run stops rather than treating an unreadable list as an empty one.
- **A candidate can be published, and is published as a candidate.** `gh release create` marks nothing
  by itself, so the archive, the checksum and the run that attached them were all one flag away from
  handing a prerelease to somebody who never asked for one; the publish step now passes `--prerelease`
  for a version with a hyphen in it, and reads the result back out of the API into its own log. The
  release gate resolves the app default at a candidate tag instead of comparing it with the tag: a
  candidate is opted into, so the default keeps naming the release a reader gets with no override, and
  a default that named the candidate itself would fail the gate (that release does not exist until the
  tag publishes). `scripts/check-release-pins.sh` carries the rule and the four cases are pinned
  against the tags they apply to.
- **A daemon whose CLI cannot report a version is replaced, not reused.** `install.sh` reads the
  installed daemon's release from `whirl --version`, and a CLI that answered nothing fell through to a
  question about its own usage, which says the CLI has daemon verbs and says nothing about which
  release it is. A daemon older than the pin was therefore kept forever, and hidden from the script
  (a minimal `PATH`, an empty prefix) the identical command installed the pin. Such a CLI predates the
  version flag, so it is now replaced like any older daemon, and the note printed says why.
- **A row for a source with nothing saved in the key store says that, and not that a key is needed.**
  A Wallhaven row over an empty store read `(needs a key)` while the line under it, built from the same
  absence, said the collection is public and needs none. Nothing saved is not a key being required; the
  row now reads `(no key is saved)`, which agrees with the state line, and where a key genuinely is
  needed the words still come from the daemon's own refusal reason.

The suite also measures its own coverage and floors it twice, and the documentation's file:line
citations were re-pointed at the tree they describe.

## Installing or upgrading

The candidate is installed by asking for it, and the channel is the short way to ask. The script has to
be one that reads the channel: `v0.2.5-rc.1` carries it, and so does `main`.

    curl -fsSLO https://raw.githubusercontent.com/guruor/whirl-ui/v0.2.5-rc.1/install.sh
    less install.sh
    WHIRL_CHANNEL=unstable sh install.sh

It resolves the newest prerelease of each repository and installs that pair: the app from
`v0.2.5-rc.1`, and the daemon from `v0.2.2-rc.3`, which is the daemon's newest prerelease. The same
pair, named:

    WHIRL_UI_VERSION=0.2.5-rc.1 WHIRL_VERSION=v0.2.2-rc.3 sh install.sh

An unstable pair is not reproducible, and the two disagreeing sentences are worth reading before
either command. The pair is whatever each repository's newest prerelease is on the day the command
runs, so the pair it installed is in the receipt rather than in the command; and `unstable` is not "the
newest build of each repository", because a repository's newest prerelease can be older than its newest
release (the daemon published `v0.2.2` after `v0.2.2-rc.3`).

Going back to the released pair is `sh uninstall.sh` and then `sh install.sh`. The second command alone
is not the way back: it replaces the app with the pinned release, and it reuses a daemon that is the
pinned release or newer, which the candidate's daemon is.

The installer verifies every download against the sha256 published beside it, keeps a receipt naming
every path it installed, and clears the quarantine flag so an upgrade asks for no second approval. The
app is ad-hoc signed and not notarized, so the first launch asks for the one Gatekeeper approval that
every unsigned build needs. `uninstall.sh` removes what the receipt names and leaves the daemon's own
state alone.
