# whirl-ui v0.2.0

Whirl is a lightweight tray frontend for the [whirl](https://github.com/guruor/whirl) wallpaper daemon.
The daemon is headless: it owns the wallpaper, the rotation, the sources and every piece of state, and
this app is a client of it. It puts the daemon on the menu bar, where the rows show what the daemon
reports and send the daemon's own verbs, and **Settings…** opens a window over the daemon's effective
plan. The app writes no state file, sets no wallpaper itself, and starts no process of its own: when the
daemon is absent it offers to start it by running the daemon's own command, `whirl daemon start`, which
asks the OS supervisor for the job the supervisor owns.

This release is **macOS only**: Apple silicon, macOS 13 or later. Windows and Linux are M4 in
[`docs/milestones.md`](../milestones.md); this release carries no build for either.

## Which build this is

The release carries one archive, built from the tagged commit by
[`.github/workflows/release.yml`](../../.github/workflows/release.yml):

    Whirl-0.2.0.zip          Whirl.app, the app bundle, at the archive's root
    Whirl-0.2.0.zip.sha256   the archive's sha256, published beside it

`Whirl.app` is `com.guruor.whirl-ui`. It is an accessory app, and it is an agent only while its window
is shut: with no window open it has no Dock icon and nothing in the app switcher, and while the settings
window is open it takes a Dock tile and appears there, so the window manager can manage the window you
were looking at.

The version is the tag. The tag is `v0.2.0`; `scripts/make-bundle.sh` strips the leading `v`, which is
why the bundle's `CFBundleShortVersionString` and the archive's own name are `0.2.0` without it.

## What changed since v0.1.0

- **Choosing a folder is the system's own folder panel.** **Add a folder…** opens `NSOpenPanel`, which
  is the picker every macOS window uses. The app's own drawn browser is still there, as the fallback for
  a build or a machine where the panel cannot be shown, and it is no longer the first thing you meet.
- **Add Wallhaven asks for the collection.** The row now asks for the collection's address, public or
  private, and the address stays editable afterwards. The token is optional, it is what a private
  collection or a raised rate limit needs, and it is stored in the keychain rather than in the config
  file. Before this release the row created a source with no collection and no query at all, which
  fetched whatever the site's API returns with no parameters.
- **The settings window is a real window.** It is in the app switcher while it is open, and clicking
  **Settings…** again raises the window you already have instead of activating the process and leaving
  the window where it was.
- **A third mark in the menu bar.** The tray now says three things rather than two: running, paused, and
  the daemon cannot be reached.
- **First launch offers to start the daemon, and quitting asks about it.** When the app starts and no
  daemon answers, the window and the menu carry a **Start whirl** control that runs `whirl daemon
  start`. Quitting asks whether to stop the daemon as well: the box is unchecked by default, so closing
  the app leaves the daemon running, and "don't ask again" remembers the answer.
- **The front page is a product page**, and the journeys a person actually takes are written down in
  [`docs/journeys.md`](../journeys.md).

## Install

There are two routes and one outcome. Both are written out, step by step, in a single place:
[`docs/installation.md`](../installation.md).

- **Route A, one command**: fetch `install.sh` from this tag, read it, then run it. It installs the
  daemon and the app, checking each archive against the sha256 published beside it before anything is
  unpacked.
- **Route B, by hand**: the same work typed out, from the Rust toolchain and the daemon's three
  binaries to a picture on the desktop and the tray app talking to the daemon.

## Which daemon this app wants

The **Start whirl** control and the quit question ask the daemon to do something through its own
command, `whirl daemon install|start|stop|status`, which arrived in **whirl v0.2.0**. With whirl v0.1.0
on `PATH` the app is a client like any other and says what the command answered, rather than pretending
it worked or reaching for a process of its own. Everything else in this release works against v0.1.0.

## The signature, and the first launch of a downloaded copy

The app is **ad-hoc signed** and **not notarized**. There is no Developer ID behind this release:
nothing on the machine verifies who built it, and `spctl -a -vv` refuses the bundle, which is expected
rather than a failure.

macOS puts `com.apple.quarantine` on anything it can tell arrived from the network, a browser download
included. Launch a quarantined copy and Gatekeeper refuses it: the app does not open, and the dialog
offers to move it to the Bin or to cancel the launch. The way through is to allow it once under
**System Settings → Privacy & Security → Open Anyway**, or to clear the flag before launching:

    xattr -dr com.apple.quarantine /Applications/Whirl.app

Quit the app first if it is running: removing the attribute from a copy that is still up is refused
with `Operation not permitted`. A copy you built or installed on this machine carries no quarantine
flag and needs none of this, and route A clears the flag on a downloaded copy itself, after its own
checksum check has passed.

## What the published checksum proves

The `.sha256` beside the archive is what it says: the archive's sha256, so it can be checked directly.

    shasum -a 256 -c Whirl-0.2.0.zip.sha256
    Whirl-0.2.0.zip: OK

It proves that the bytes you have are the bytes the release job built. It proves nothing about who
built them. It is a delivery check, not an identity, and it is not a signature.

## Known limits

- **`whirl daemon …` is the daemon's macOS surface.** The control appears on macOS, which is the only
  platform this build ships for, and the daemon's own command refuses in one sentence on the platforms
  it has no unit for.
- **Unregistering the login item leaves a record.** The app registers its own login item through
  `SMAppService`, and `--login-item unregister` removes it from the Login Items pane. The Background
  Task Management database keeps the app's row as `Disposition: [disabled, allowed, notified]`, because
  `SMAppService` has no delete. Nothing a person can see in the Login Items pane outlives an unregister;
  the database row does. It is stated in [`docs/milestones.md`](../milestones.md) M3 criterion 1.
- **macOS only, in this release.** There is no Windows or Linux artifact.
- **A real login is still unproven.** The app asks the daemon's command, and the daemon's command writes
  the unit, but nothing in this release has yet started a daemon by rebooting a machine.
