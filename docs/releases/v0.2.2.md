# whirl-ui v0.2.2

Whirl is a lightweight tray frontend for the [whirl](https://github.com/guruor/whirl) wallpaper daemon.
The daemon is headless: it owns the wallpaper, the rotation, the sources and every piece of state, and
this app is a client of it. It puts the daemon on the menu bar, where the rows show what the daemon
reports and send the daemon's own verbs, and **Settings…** opens a window over the daemon's effective
plan. The app writes no state file, sets no wallpaper itself, and starts no process of its own.

This release is **macOS only**: Apple silicon, macOS 13 or later.

## Which build this is

The release carries one archive, built from the tagged commit by
[`.github/workflows/release.yml`](../../.github/workflows/release.yml):

    Whirl-0.2.2.zip          Whirl.app, the app bundle, at the archive's root
    Whirl-0.2.2.zip.sha256   the archive's sha256, published beside it

The version is the tag: `v0.2.2`, with the leading `v` stripped by `scripts/make-bundle.sh`.

## What changed since v0.2.1

Nothing in the app behaves differently. This release exists because the install script that v0.2.1
served installed the release before it.

- **`install.sh` installs the release it is served from.** The two releases the script installs are
  hand-kept defaults of its own, `WHIRL_UI_VERSION` and `WHIRL_VERSION`, and nothing compared them
  with the tag the script is served from. v0.2.1 was tagged with both of them still reading 0.2.0, so
  the route the v0.2.1 notes documented,
  `raw.githubusercontent.com/guruor/whirl-ui/v0.2.1/install.sh`, installed 0.2.0. The release page,
  the archive and the checksum were all correct; only the script a reader runs pointed at the release
  before it. The app default now names 0.2.2. The daemon default names v0.2.1, unchanged, because
  `whirl` releases on its own schedule and v0.2.1 is its latest.
- **A release whose script names another release builds nothing.** `scripts/check-release-pins.sh
  <tag>` asks two questions of a tag: does the app default name it, and does the daemon default name a
  daemon release that exists. The first is exact and offline; the second resolves the archive, because
  `whirl` and `whirl-ui` are released independently and the daemon pin normally trails this tag. The
  release workflow runs it in a `pin` job between `guard` and `bundle`, which `bundle` names in
  `needs:`. The check fails closed: a pin that cannot be read, or a daemon release that cannot be
  reached, is a failure and not a pass.
- **CI runs the install scripts, which nothing ran before.** `scripts/test-install.sh` had no caller,
  which is how both defects below reached a tag. A macOS `install` job runs it now, and
  `CONTRIBUTING.md`'s release path names the pin bump as a step, because the defaults are hand-kept.
- **`install.sh` and `uninstall.sh` ask the daemon for its login unit with a verb that exists.** Both
  asked for `whirl service install` and `whirl service uninstall`, behind a guard that read the CLI's
  own usage for `^  service`. No released CLI lists that verb, so the call was never made: nothing
  came up at login, and the receipt carried no `unit` line, so `uninstall.sh` then reported that this
  install had never put a unit there. Both scripts now read the verb out of the CLI's usage,
  `daemon install` first and the older `service` name second for a CLI that carries it.

## Installing or upgrading

The installer is the same one command, and it is safe to run over an existing install: it verifies
every download against the sha256 published beside it, replaces the app, and replaces an older daemon
with this release's.

    curl -fsSL https://raw.githubusercontent.com/guruor/whirl-ui/v0.2.2/install.sh | sh

**If you installed from the v0.2.1 notes, that run installed 0.2.0.** The line above installs 0.2.2.
To stay on 0.2.1 instead, pass the pair the script would otherwise read from its own defaults:

    WHIRL_UI_VERSION=0.2.1 WHIRL_VERSION=v0.2.1 sh install.sh

The app is ad-hoc signed, not notarized, so the first launch after an upgrade asks for the one
Gatekeeper approval that every unsigned build needs. The installer clears the quarantine flag so no
second approval is asked for. `uninstall.sh` removes what was installed and leaves the daemon's own
state alone.
