# A report a tester can send

What this app should build so that a person testing a whirl-ui build on a machine we cannot reach
can hand us a log we can act on, without that log carrying anything private. Written 2026-10-04.
Research and a recommendation only: no code changes here. Every "product X does Y" claim carries the
source it came from, quoted beside it, so a reader can re-open it.

Scope, from the maintainer's own framing:

> we can see if we can add some kind of reporting mechanism so when testing on different os we
> should be able to report the logs to the developer. Make sure the logs doesn't contain any private
> or secret info. The logs should be self sufficient so we can understand how the app is behaving
> without missing any critical detail. We can research for best option other cross-platform free apps
> use for this and we can follow the same. We can add this as future work in milestone.

The parked entry lives in `docs/milestones.md`; the list is this file, and nowhere else.

## 1. The problem, as measured

Two defects from one day, and neither left anything behind for the person reporting it.

- **The black window.** A menu bar app opened an empty window at launch, cleared with the renderer's
  own clear colour. The cause was found and fixed on the window's own branch: "eframe 0.36.2 does
  not honour `visible` for a root window: `post_rendering` calls `window.set_visible(true)` after the
  first painted frame whatever the builder asked for" (the fix's own commit message; its subject is
  "The menu bar window is on screen only while a dialog is in it"). The fix adds "one line per change goes to
  stderr, the app's only log". Before the fix, a person who saw a black window had nothing to send.
- **The repeated Gatekeeper refusal.** The bundle the release path builds is ad-hoc signed by
  `scripts/make-bundle.sh` (`codesign --sign -`), which the build script prints, and macOS rejects an
  ad-hoc, un-notarized bundle: that work's own commit message records `spctl -a -vv dist/Whirl.app`
  printing `dist/Whirl.app: rejected`, exit 3, and `syspolicy_check` printing `Adhoc Signed App`.
  whirl's `docs/decisions/0001-macos-artifacts-ship-unsigned-in-v0.1.0.md` is the price decision:
  Developer ID signing plus notarization needs "the Apple Developer Program membership, **99 USD per
  membership year**". A refusal happens *before the app runs*, so a report generated by the app
  cannot describe the refusal at all.

And the asymmetry the maintainer named:

- **The app writes almost no log at all.** It has no logging crate (`crates/whirl-ui/Cargo.toml` has
  none) and no log file. Its whole output is `eprintln!`/`println!`: usage and error lines in
  `crates/whirl-ui/src/main.rs` and `dump.rs`, and one line per menu change plus its errors in
  `crates/whirl-ui/src/tray.rs:149-172` (`fn changed` prints `whirl-ui: {unix_nanos} now: {line}`).
  When the app is launched from Finder as a bundle there is no terminal, so stderr goes nowhere.
- **The daemon logs to a file.** `crates/whirl-core/src/config.rs::log_file()` resolves
  `~/Library/Logs/whirl/whirl.log` on macOS, and whirl's `docs/spec/state-and-cache.md` 1.1 says:
  "`~/Library/Logs/whirl/whirl.log` | The log, one file rotated at 1 MiB, three kept. | Yes.
  Diagnostics only." So one half of a rotation is retained and the other half is not.

The target: a tester on a machine we cannot reach runs one thing and gets a text bundle that is
self-sufficient (section 3) and secret-free (section 4).

## 2. What free, cross-platform apps actually do

Five patterns. For each: what the tester does, what the developer receives, what it costs, what
account or service it needs, and what it leaks. Each is cited to a real product.

### A. "Copy diagnostics" onto the clipboard

| | |
|---|---|
| Tester does | opens a diagnostics page and presses Copy |
| Developer receives | the pasted text, pasted into a bug report by the tester |
| Cost | free, no account |
| Service | none |
| Leaks | whatever the app chooses to put in the bundle; the app can suppress the risky fields |

**Firefox** is the reference product, and its own source carries both halves. The page's title is
`page-title = Troubleshooting Information` and the button is
`copy-text-to-clipboard-label = Copy text to clipboard` (with a raw-data variant,
`copy-raw-data-to-clipboard-label`), in `toolkit/locales/en-US/toolkit/about/aboutSupport.ftl`
(<https://searchfox.org/firefox-main/source/toolkit/locales/en-US/toolkit/about/aboutSupport.ftl>);
the page and its copy logic are `toolkit/content/aboutSupport.js`. The clipboard is the whole
mechanism: the tester pastes the text into the bug report and the app sends nothing itself, so the
reference product for "copy diagnostics" is also the one that decides field by field what is safe to
put in.

**VS Code** does the same thing with a twist: Help > Report Issue opens a prefilled GitHub issue,
and when the payload is too big it copies to the clipboard instead. VS Code's own dialog, quoted in
the issue: "There is too much data to send to GitHub directly. The data will be copied to the
clipboard, please paste it into the GitHub issue page that is opened."
(<https://github.com/microsoft/vscode/issues/100054>; the flow is documented at
<https://github.com/microsoft/vscode-wiki/blob/main/Submitting-Bugs-and-Suggestions.md>).

### B. A log directory plus an export command

| | |
|---|---|
| Tester does | runs an export command (or a menu item) that writes a file or a zip |
| Developer receives | the file, attached or emailed |
| Cost | free, no account |
| Service | none |
| Leaks | the log's own contents; the app redacts what it can and the tester is told to check |

**Syncthing** is the closest product, and it is Go and readable. `GET /rest/debug/support`
"Collects information about the running instance for troubleshooting purposes. Returns a 'support
bundle' as a zipped archive, which should be sent to the developers after verifying it contains no
sensitive personal information. Credentials for the web GUI and the API key are automatically
redacted already." (<https://docs.syncthing.net/rest/debug.html>). The bundle plus its redaction
note is the pattern to copy: a zip, an allow-list, and a sentence telling the tester to look first.

**Joplin**: the tester opens "Help > Open Profile Directory", reads `log.txt` and the crash dumps
`joplin_crash_dump_<DATE_TIME>.json`, and attaches them; auto-upload is optional
(<https://joplinapp.org/help/apps/debugging>). Joplin also warns "be sure to check the log for and
remove any sensitive data": the caveat that a manual path needs because the app cannot know what a
log line might contain.

**OBS Studio** offers both halves: "Help menu > Log Files > Upload Last Log File" (sent to OBS's
server, next pattern) and "Show Log Files", which "will open the directory on your PC where OBS logs
are stored. Copy the file ... to a location convenient for you"
(<https://obsproject.com/forum/threads/please-post-a-log-with-your-issue-heres-how.23074/>).
**Signal Desktop** has the same fallback for when the app will not start: "ZIP/Compress the logs
folder ... Share the logs folder or a specific log from within the logs folder as an attachment to
support@signal.org" (<https://support.signal.org/hc/en-us/articles/360007318591-Debug-Logs-and-Crash-Reports>).

### C. An in-app report form that posts to a hosted endpoint

| | |
|---|---|
| Tester does | fills a small form in the app and presses Send |
| Developer receives | the bundle at a URL the tester pastes into the issue |
| Cost | free only where the project runs its own endpoint |
| Service | yes: a running server (unless self-hosted) |
| Leaks | metadata the redaction cannot remove; Element's own docs say so |

**Element** is the clean citation, and it is open source. "Under `Help & About`, click `Submit debug
logs` ... Enter a GitHub issue link and a description. Then click `Send logs`"
(<https://docs.element.io/latest/element-support/submit-debug-logs>). Its endpoint is the "rageshake
server", and Element's own docs state the leak exactly: "Logs are designed to not contain any truly
private data such as message content or private keys. However, they do contain metadata such as
user, room and event IDs" (<https://docs.element.io/latest/element-server-suite-pro/administration/customize-rageshake-server>).
The server is not even Element's product: "It is available at matrix-org/rageshake as an open source
software" (<https://github.com/matrix-org/rageshake>, Apache-2.0). So the pattern is self-hostable,
but it is a service to run.

**OBS** posts to OBS's own server and hands back a URL: "Click on the 'Copy URL' button to copy the
link to your clipboard" (<https://obsproject.com/forum/threads/please-post-a-log-with-your-issue-heres-how.23074/>);
the dialog carries a privacy notice before the upload: the log-upload dialog's
`LogUploadDialog.Labels.PrivacyNotice` reads "Please read the Privacy Policy and its section
regarding file uploads before uploading any files." (`frontend/data/locale/en-US.ini`,
`github.com/obsproject/obs-studio`). **Signal Desktop**'s
`Submit` > `Copy Link` is the same shape.

### D. A crash-reporting service's free tier

| | |
|---|---|
| Tester does | nothing; a crash is captured and reported automatically |
| Developer receives | a grouped crash with a stack trace in a dashboard |
| Cost | free tier for a hosted account; self-host is free but heavy |
| Service | yes, an account (hosted) or your own server |
| Leaks | the crash payload and any breadcrumbs; the vendor is a third party |

**Sentry** is the one to cite because it is both a free tier and self-hostable. Hosted: the "Free
Developer Plan" is "For solo devs working on small projects" with "One user"
(<https://sentry.io/pricing/>). Self-hosted: "consider self-hosted as the Business plan without any
software limitations and no paid tier", but "We require at least Docker 19.03.6 and Docker Compose
2.32.2" and "4 CPU Cores / 16 GB RAM + 16 GB swap" minimum
(<https://develop.sentry.dev/self-hosted/>). Self-hosting therefore needs Docker and a 16 GB machine,
which this project does not assume; the free tier instead means an account and a third party holding
the data. **Crashpad** (<https://github.com/chromium/crashpad>) and **Breakpad** are
the open-source capture libraries with no service attached, but you still have to run a collector to
receive their output.

### E. The platform-native route

| | |
|---|---|
| Tester does | runs a platform log query and sends the output |
| Developer receives | the platform's log lines for the app |
| Cost | free, no account |
| Service | none |
| Leaks | the system log is the whole machine's, not the app's; a query has to be narrow |

- **macOS**: "log is used to access system wide log messages created by os_log, os_trace and other
  logging systems"; `log show --predicate 'subsystem == "com.example.my_subsystem"'` filters to one
  app, and `log collect --last 2h --output logs.logarchive` snapshots a window
  (<https://ss64.com/mac/log.html>). A vendor tutorial shows the tester-side command in practice:
  `log show --predicate 'processImagePath CONTAINS[c] "Finder"' --last 30m`
  (<https://www.roundfleet.com/tutorial/2025-07-07-fetch-device-logs-macos>).
- **Windows**: `wevtutil epl <Path> <Exportfile>` "Exports events from an event log ... to the
  specified file", e.g. `wevtutil epl System C:\backup\system0506.evtx`
  (<https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/wevtutil>).
- **Linux**: journald "collects and stores logging data" and "The systemd service manager invokes
  all service processes with standard output and standard error connected to the journal by
  default", so a user service's output is `journalctl -u <unit>`
  (<https://man7.org/linux/man-pages/man8/systemd-journald.service.8.html>).

The platform route is free and needs no account, but it is the platform's log, not ours: the app
only gets there by writing to `os_log`/the event log/journald, and the tester still has to run a
command with the right predicate. That is why it is a complement, not the mechanism.

### What the survey settles

- The **copy-diagnostics** and **log-directory-plus-export** patterns are the only two that need no
  account and no service. Every other pattern buys convenience with a service (C, D) or with the
  platform's own firehose (E).
- The two patterns that fit this product's constraints are also the two with the strongest
  precedent for **preview-before-send** and **allow-listed fields** (Firefox decides field by field
  what goes in; Syncthing redacts its bundle).
- Sending the bundle somewhere is a separate decision from building it, and the constraints answer
  it: no account, no service (section 5).

## 3. What has to be in a report for it to be self-sufficient

A **field**, not a category. The left column is the field name the report emits; the middle is where
it comes from; the last two say what it would have told us about the two defects.

### App side (the app already has all of these)

| field | source | black window | repeated refusal |
|---|---|---|---|
| `app_version` | `env!("CARGO_PKG_VERSION")` | which build drew the window | which build was refused |
| `app_build` | the git commit, baked in at build | pins the report to a commit | pins the artifact |
| `bundle_id` | `CFBundleIdentifier` (`com.guruor.whirl-ui`) | identifies the app as launched | the identity `spctl` rejected |
| `os` | `sw_vers -productVersion` + the arch | one macOS version per report; the window bug reproduced on one | the refusal is version-specific |
| `app_log_tail` | the app's own last N stderr lines (the tray's per-change lines) | the line "one line per change" *was* the fix; without it, absence of a line is the evidence | (a refused launch writes none; see below) |
| `window_visibility` | each show/hide the app performed, with a timestamp | the whole defect: a launch that presented a window and should not have | n/a |
| `bundle_signature` | `codesign --display --verbose` flags (`adhoc` vs a Developer ID) | n/a | names the property that makes `spctl` reject it |
| `quarantine` | whether the bundle carries `com.apple.quarantine` | n/a | a quarantined ad-hoc bundle is the exact refusal |
| `launch_context` | launched from Finder / launchd / a terminal, and the bundle path's **leaf** | whether stderr had anywhere to go | whether the user double-clicked the download |

`app_log_tail` and `window_visibility` together are the field that would have made the black window
self-sufficient: the fix is literally a line on stderr per visibility change, and today that line
dies with the terminal. On the refusal, the honest finding is in the table: **a refused launch
produces no report at all**, because the process never starts. The fields above narrow a refusal that
a *later* successful launch can describe; for the refusal itself the report's content is its own
absence, and the fix is the release path (`docs/decisions/0001-...`), not the reporter.

### Daemon side (the socket already answers all of these; section 2.10 and 2.5 of whirl's `docs/architecture.md`)

| field | source | black window | repeated refusal |
|---|---|---|---|
| `daemon_version` | `version` → `daemon_version:` | which daemon the app was talking to when the window was drawn | n/a |
| `protocol` | `version` → `protocol:` | a client/daemon mismatch is a real black-window candidate | n/a |
| `platform` | `version` → `platform:` | the OS the app ran on | the OS the refusal happened on |
| `daemon_connection` | the client's own result: reachable, or unreachable with the socket **leaf** and mode | an app that never found the daemon still opens a window: that was the empty window | n/a |
| `socket_exchange` | the report's own `status` call: `OK`, or the `ERR` code and message | the exact verb that failed first | n/a |
| `config_shape` | which keys the config sets, as booleans (never values) | whether `display.mode` or a source shape was in play | whether a hand-edited config is the difference |
| `history_tail` | `history <n>`: the last N entries, each with `via` and its digest | n/a | n/a |
| `last_error` | `status` → `last_error` (an error code, `-` on success) | a rotation that failed while the window was up | n/a |
| `last_via`, `last_at` | `status` | which path (source/startup/external) produced the current image | n/a |
| `sources` | `status` `source:` records: `enabled`, `last=`, `reason=` | a `last=error` beside a visibly unchanged wallpaper | n/a |

`history_tail`, `last_error`, `sources.last/reason` and `last_via` together are the "last N rotations
with their outcomes and reasons" a report needs: each history entry carries its `via` (whirl
2.11 transcript, `entry: <time> <via> <origin_key> <digest> <path>`) and each source record carries
`last=` and `reason=`. Every error is a typed code from the closed set (`Refusal` in
`crates/whirlui-client/src/error.rs`), so "any error with its code" is already the protocol's own
vocabulary, not something the app invents.

## 4. What must never be in a report, and the mechanism

The rule, then the mechanism that enforces it rather than trusting the intention.

### The rule

1. **The Wallhaven token.** Neither `api_key_ref` (a label such as `keychain:whirl-wallhaven`) nor
   anything it resolves to. The label is already a name and not a value: `crates/whirl-ui/src/keychain.rs`
   defines `LABEL` and its own doc says "It is a name, never a value". Whirl 6.3: "The config file
   holds a reference, never a value ... a key in a config file is a key in every backup of that
   file."
2. **The maintainer's and the tester's home path.** Any absolute path. Whirl's `status` carries
   `state_dir`, `cache_dir`, `anchor_path`; `history` entries carry image paths; `config path` is one.
   The report redacts each to its leaf name or a short hash.
3. **File names from a pictures folder.** A local source's `paths` and a history entry's path are
   the tester's private files. Same treatment as (2): leaf name or hash, never the full path.
4. **The collection's contents.** Never image bytes, never a favourite's file. Favourites are named
   by digest or redacted name at most.
5. **Cookies and any environment value.** The report reads nothing from the environment. (Whirl
   already scrubs the worker's environment for the same reason: "the worker's environment is
   scrubbed, not inherited", `docs/architecture.md` 6.2.)
6. **Anything the control socket echoes from the config that is a value.** `config path` echoes an
   absolute path; `status` echoes `state_dir`, `cache_dir`, `anchor_path`. The report must pass every
   socket line through the redactor; it may not paste a raw line.

### The mechanism

Four parts, each of which a test can hold:

1. **An allow-list by construction.** The report is a Rust struct with named fields, serialized by
   `serde`. A value with no field has nowhere to go; there is no free-form string the report copies a
   socket line into. This is already this repository's idiom: `Refusal` carries only `code` and
   `message`, and `Socket` deliberately reports "the socket file's *name* and its mode ... nothing
   here prints a directory" (`crates/whirlui-client/src/error.rs`). The report composes the same way.
2. **A `Redacted` newtype for every path.** A path can only enter the report as
   `Redacted::of(path)`, which stores the leaf name and a short `sha256` prefix and never the full
   path. Local sources get this for free where the protocol already hashes them: whirl 2.5 makes a
   local `origin_key` the `sha256` of the absolute path. The tests below assert the property at the
   only door a path can use.
3. **A planted-secret test.** `report::tests::a_planted_secret_never_reaches_the_report` plants a
   known fake token in every string a report can draw from (the config's `api_key_ref`, the keychain
   metadata, an `ERR` message, a history path, a source `paths` entry, and a fake `$HOME`), builds
   the report, and asserts the token, the planted home path and the planted picture file name do not
   appear anywhere in the serialized bytes. It is the direct descendant of two tests already in the
   tree: `the_write_line_carries_the_token_only_as_hex_on_stdin` and
   `an_attribute_dump_loses_any_line_that_carries_a_password` (`crates/whirl-ui/src/keychain.rs`),
   which hold the same property for the write path and the store dump.
4. **The test must fail when the redactor is bypassed.** A second assertion, in the same test, that
   the same planted value *does* appear if it is written through a raw field of the struct's own test
   double, so the test proves it is checking the door, not a value that was harmless anyway. This is
   the rule whirl's own log states and the report adopts: "the log holds no secret and no image
   bytes ... the log is 0600, but it is also copied into bug reports" (`docs/architecture.md` 6.2).

The tester also **sees the bundle before sending it** (section 5), which is the last check a
mechanism cannot make for itself.

## 5. How it reaches the developer

The constraints decide most of this: no account, no service the maintainer cannot run or read, free,
and the tester must see what they are sending before they send it.

| option | what it needs | cost | fits? |
|---|---|---|---|
| A zip the tester emails or attaches | the tester finds the file and attaches it | free, no account | yes, but asks the tester to locate a file in a log directory |
| A paste of the bundle's text | nothing | free, no account | yes, and it is what Firefox and VS Code do |
| A URL the app opens in the browser | a hosted endpoint to POST to | a service, unless self-hosted | no: it is the service the constraints rule out |
| An in-app upload | a running endpoint (rageshake, Sentry) | a service, unless self-hosted | no, for the same reason; heaviest to run |

**Recommendation: one text bundle, shown in the window, with Copy to clipboard and Save to a file.**
The tester presses "Report…", reads the exact text (the section-3 fields, redacted as in section 4),
and either copies it into whatever channel they already have (a forum post, an email, a chat) or
saves it and attaches the file. The app needs to know no channel and run no server.

Why this one: it is the intersection of the two patterns that need no account (A and B), it keeps
the preview the constraints require, and it matches this repository's own idiom: the headless dump
modes already print text a test can assert (`--dump-status`, `--dump-settings`), so a `--report`
mode is one more text mode and the window is a copy of it. What the others cost: the URL and upload
options each need a service to run and to keep running; a bare zip asks the tester to find a file in
a directory they have never seen; a bare clipboard paste loses the "attach" path when the text is
long. This carries both.

## 6. What to build first, and what can wait

The survey is much larger than v0.1 needs. The smallest slice that makes a tester's defect
self-sufficient, in order:

1. **The report module and the `--report` mode.** An allow-listed struct (section 3), the `Redacted`
   newtype, the planted-secret test (section 4), and a headless mode that prints it. No window, no
   file, no network: a test can assert every line. This is the whole value of the work and the
   smallest thing that delivers it.
2. **A durable app log.** Send the app's own lines (the tray's per-change and error lines, and the
   window-visibility lines the black-window fix added) to a file the report can tail,
   `~/Library/Logs/whirl/whirl-ui.log`, the daemon's directory and the app's own file. This is what
   turns `app_log_tail` from empty to evidence, and it is the one piece that needs a new platform
   path.
3. **The window's "Report…" pane.** Show the same text with Copy and Save (section 5).

Deliberately left out of v0.1:

- **No crash-reporting service** (Sentry or otherwise): an account, a third party, or Docker this
  machine does not have.
- **No in-app upload / rageshake**: a service to run and keep running.
- **No platform-native log harvesting** (`log show`, `wevtutil`, `journalctl`): the app would have to
  write to the platform's log first, and the tester would still run the query. A follow-up once
  `--report` exists, not a prerequisite.
- **No collection or image contents, ever**: the rule in section 4 is permanent, not deferred.

The refusal above still needs the release path (notarization) rather than the reporter; the report
narrows it, it does not remove it.
